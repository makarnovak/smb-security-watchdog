# Watchdog Pilot — Технічна архітектура сторожа для Google Workspace / Microsoft 365

**Лінія:** ШІ-агенти безпеки для SMB
**Пілот:** власний Workspace власника
**Версія:** 0.1 — 2026-11-24
**Принцип №1:** Агент реагує **ТІЛЬКИ оборотним блокуванням**. Нічого не видаляє, нічого не руйнує. Кожна дія має задокументований відкат, а відкат — в 1 тап власника.

---

## 1. Що це і чого це НЕ робить

Watchdog — постійно активний сторож поверх Google Workspace і/або Microsoft 365 малої фірми (10–200 людей, власного безпековика немає).

**Робить:**
- безперервно читає аудит-логи входів, пошти, файлів та OAuth-грантів;
- виявляє вузький набір високосигнальних аномалій (детектори D1–D7, §5);
- при спрацюванні — виконує **оборотне** стримування: скид пароля + вбивство сесій, тимчасова заморозка акаунта, карантин листа, закриття публічного лінка;
- **до** дії зберігає незмінний пакет доказів (evidence bundle, §6);
- надсилає власнику сигнал із вердиктом і трьома кнопками: `Відкотити` / `Тримати блокування` / `Ескалювати`.

**НЕ робить (заборонено дизайном, не лише політикою):**
- не видаляє акаунти, листи, файли, правила — у сервісного акаунта агента **фізично немає delete-прав** (§8);
- не змінює вміст документів і листів;
- не приймає незворотних рішень; заморозка акаунта довше за поріг — тільки з підтвердженням людини (§7);
- не є антивірусом / EDR / фаєрволом і не замінює їх — це шар identity + SaaS-audit response.

## 3. Джерела сигналів (детально)

### 3.1 Google Workspace

| Джерело | Що беремо | Детектори |
|---|---|---|
| Admin SDK **Reports API** — `activities.list(applicationName=login)` | успішні/невдалі входи, IP, `login_failure`, `login_success`, `logout`, `sensitive_action` | D1, D5, D6 |
| Reports API — `drive` | `download`, `view`, `create`, `change_acl` (зміна доступу), `edit` | D2, D3 |
| Reports API — `token` | OAuth-гранти: `authorize`, app name, scopes | D7 |
| Reports API — `admin` / `user_accounts` | створення forwarding, зміна 2-Step, recovery, delegations | D4 |
| **Alert Center API** | готові Google-алерти (suspicious login, data leak, gov-backed attack) — як додатковий вхід, не єдиний | D1, D5 |
| **Gmail API** | `users.settings.forwardingAddresses`, `filters.list` (forward/delete rules), `messages.get` (метадані підозрілого листа для карантину) | D4, карантин |
| **Drive API** | `permissions.list` по файлу (тип `anyone`), `files.get` (назва, власник, MIME) | D3 + дія restrict |
| **Directory API** | `users.get/list`: `lastLoginTime`, `suspended`, `creationTime`, orgUnit | D6, контекст |

Доступ: Domain-Wide Delegation на сервісний акаунт, impersonation — **тільки read-only admin-акаунт сторожа**; write-операції — окремим вузьким scope-набором (§8). Polling 60–300 с (Reports API має затримку публікації подій — враховано в порогах: вікно детектора ≥ вікно доставки + запас).

### 3.2 Microsoft 365

| Джерело | Що беремо | Детектори |
|---|---|---|
| **Entra ID sign-in logs** (MS Graph `auditLogs/signIns`) | результат входу, IP, location, deviceDetail, `riskState`, conditional access | D1, D5, D6 |
| **MS Graph Security** (`security/alerts_v2`, incidents) | готові алерти Defender/Entra ID Protection (risky user, impossible travel від Microsoft) — кореляція з нашими детекторами | D1, D5 |
| **Unified Audit Log** (Office 365 Management Activity API) | `FileDownloaded`, `SharingSet`/`AnonymousLinkCreated`, `New-InboxRule`, `Set-Mailbox` (forwarding), `Consent to application` | D2, D3, D4, D7 |
| **Graph — Outlook settings** | `mailFolders/inbox/messageRules`, `mailboxSettings` (automaticReplies / forwarding) | D4 |
| **Graph — Drive/SharePoint** | `permissions` по item (link scope `anonymous`), `driveItem` metadata | D3 + дія restrict |
| **Graph — users** | `signInActivity` (потребує Entra ID P1/P2), `accountEnabled`, `lastPasswordChangeDateTime` | D6 |

Доступ: зареєстрований Entra app, **application permissions, мінімальний набір** (§8), admin consent власника тенанта. Graph subscriptions (webhook) на signIns де доступно + polling fallback.

### 3.3 Нормалізована подія

Обидві платформи зводяться в один `Event`: `{ts, platform, actor, action, ip, country, device_id, object_type, object_id, object_name, details{}}`. Детектори платформонезалежні; платформозалежний тільки шар Ingestion та ActionEngine-адаптери.

## 4. Модель загроз

**Захищаємо:** акаунти співробітників і власника, пошту (Gmail/Exchange), файли (Drive/OneDrive/SharePoint), фінансові та контрактні документи SMB-клієнта.

**Атакуючий (реалістичний для SMB):**
1. Зовнішній фішер — викрав пароль (credential phishing, AiTM-проксі), заходить із чужої країни/пристрою, ставить forwarding rule, тягне файли. → D1, D4, D5, D2
2. Password spray / brute-force ботнет проти слабких паролів без MFA. → D5
3. Звільнений/забутий акаунт — dormant обліковка підрядника чи екс-співробітника, яку ніхто не вимкнув; її підбирають або нею зловживає інсайдер. → D6
4. Інсайдер або скомпрометований акаунт публікує чутливий файл «anyone with the link». → D3, D2
5. Shadow OAuth — співробітник (або атакуючий від його імені) видає широкі права сторонньому застосунку («читати всю пошту й файли») — тиха постійна ексфільтрація без входів. → D7
6. BEC (business email compromise) — скомпрометована скринька розсилає фейкові інвойси; відповідь сторожа — карантин підозрілих листів + freeze скриньки. → D4/D5 → карантин

**Поза моделлю пілота:** malware на ендпоінтах, ransomware на серверах клієнта, фізичний доступ, компрометація самого Google/Microsoft, соц-інжиніринг власника поза цифровими слідами. Це чесно вказано клієнту в пропозиції.

**Припущення:** у тенанті ввімкнено аудит-логи (Google: за замовчуванням; M365: Unified Audit Log — перевірка на онбордингу — крок №1 чекліста), годинники джерел синхронні (працюємо у UTC), власник має канал, куди сигнал дійде за хвилини (email + chat).

## 5. Детектори: поріг → дія → відкат

Усі дії оборотні. «Freeze» = `suspended=true` (Google) / `accountEnabled=false` (Entra) на обмежений строк із запланованим авто-розмороженням.

| ID | Детектор | Поріг спрацювання (пілот) | Severity | Дія (автоматична, оборотна) | Як відкотити (rollback-рецепт) |
|---|---|---|---|---|---|
| **D1** | Impossible travel / дивний вхід | Успішний вхід із нової країни **і** нового device < 2 год після попереднього входу з іншої країни, фізично несумісної за часом перельоту | High | Скид пароля + revoke всіх сесій/токенів; сигнал власнику (L1) | Власник тисне «Відкотити»: сесії не відновлюються (це небезпечно), натомість юзеру видається тимчасовий пароль / лінк скидання — «відкат» тут = контрольоване повернення доступу людині, а не старих токенів атакуючому |
| **D2** | Масове скачування файлів | > 20 download-подій за 10 хв одним актором (пілотний поріг; тюниться під клієнта) | High | Freeze акаунта на 4 год + revoke сесій; збереження переліку файлів у bundle | `unsuspend` / `accountEnabled=true` в 1 тап; авто-розморозка через 4 год, якщо власник не продовжив |
| **D3** | Публічний лінк на чутливий файл | Створено permission `anyoneWithLink`/`anonymous` на файл, у назві/шляху якого є ключові слова: `finance, password, contract, payroll, invoice, tax, банків, пароль, договір` (список — у конфігу клієнта) | Medium | Закрити публічний доступ: permission → `restricted` (Google) / видалити anonymous link, залишити named permissions (MS); сигнал власнику (L1) | Повторно створити `anyoneWithLink`-permission — 1 тап; оригінальний permission-обʼєкт збережено в bundle дослівно |
| **D4** | Forwarding rule / делегування назовні | Створено Gmail filter / forwarding address / Inbox rule з пересиланням чи делегуванням на **зовнішній** домен (не домен клієнта) | High | Вимкнути правило (disable, **не видаляти**), лист-підтвердження forwarding — у карантин; freeze — тільки за L2-підтвердженням | Re-enable правила в 1 тап; правило збережено в bundle цілком (умови + дії) |
| **D5** | Brute / spray, потім успіх | ≥ 5 невдалих входів за 15 хв по акаунту **і** після них успішний вхід за 60 хв | High | Як D1: скид пароля + revoke сесій; якщо невдалі тривають — freeze на 4 год | Як D1; freeze — авто-розморозка / 1 тап |
| **D6** | Dormant-акаунт ожив | `lastLoginTime` > 90 днів тому (або ніколи) **і** новий успішний вхід | Medium–High | Revoke сесій + скид пароля; freeze до рішення власника, максимум 24 год (L2 на продовження) | 1 тап: розморозити + видати лінк скидання пароля легітимному власнику акаунта |
| **D7** | OAuth-грант із широкими правами | Новий сторонній застосунок (не з allowlist клієнта) отримав scope рівня: читання всієї пошти, повний Drive, `offline_access` — будь-які 2+ | Medium | Revoke цього OAuth-гранта (тільки цього застосунку, акаунт не чіпаємо); сигнал власнику (L1) | Повторна авторизація застосунку юзером — сторож фіксує її як свідомий allowlist-запис після підтвердження власника |

**Карантин листа** (допоміжна дія, не окремий детектор): підозрілий лист (з правила D4, BEC-ознаки, або ручна команда техніка) переміщується у карантинний label/folder `WATCHDOG/QUARANTINE` зі збереженням оригінальних заголовків у bundle. Відкат: повернути лист у Inbox в 1 тап. Лист **не видаляється ніколи**.

## 6. Evidence bundle — формат

Один інцидент = один bundle. Записується **до** дії, атомарно (tmp → fsync → rename).

```json
{
  "bundle_version": 1,
  "incident_id": "inc-20261124T053000Z-a1b2c3",
  "created_at": "2026-11-24T05:30:00Z",
  "platform": "google | microsoft",
  "tenant": "example (pilot)",
  "detector": {"id": "D1", "name": "impossible_travel", "severity": "high"},
  "actor": "user@example.com",
  "trigger_events": [ { "ts": "...", "action": "login_success", "ip": "...", "country": "XX", "device_id": "...", "raw_ref": "reports-api:<activity-id>" } ],
  "context_snapshot": {
    "account_state_before": {"suspended": false, "last_login": "..."},
    "affected_objects": [ {"type": "file|rule|grant|message", "id": "...", "state_before": { "...дослівний обʼєкт доступу/правила..." }} ]
  },
  "actions_taken": [ {"action": "revoke_sessions", "dry_run": true, "at": "...", "result": "simulated|ok|failed"} ],
  "rollback_recipe": [ {"undo": "issue_password_reset_link", "for_action": "force_password_reset"}, {"undo": "unsuspend_account", "for_action": "suspend_account", "auto_at": "..."} ],
  "owner_decision": {"decision": null, "at": null, "by": null},
  "hashes": {"canonical_sha256": "<sha256 канонічного JSON без цього поля>", "prev_bundle_sha256": "<хеш попереднього bundle у ланцюгу>"}
}
```

Цілісність:
- **SHA-256** по канонічній серіалізації (sorted keys, UTF-8) всього bundle без поля `hashes`;
- **hash-chain:** кожен bundle містить хеш попереднього → підміна/видалення старого bundle ламає ланцюг і виявляється верифікацією;
- **append-only JSONL-індекс** (`evidence/index.jsonl`): рядок на bundle `{incident_id, sha256, prev_sha256, ts}` — тільки дописування, файл відкривається в режимі `a`, жодного перезапису;
- у продукті: дзеркалювання bundle у сховище з Object Lock / retention (GCS Bucket Lock або Azure Immutable Blob) — у пілоті це задокументований наступний крок, локально ланцюг виконує ту саму роль для демо.

## 7. Human-in-the-loop — рівні

| Рівень | Коли | Поведінка |
|---|---|---|
| **L0 — auto, тихий лог** | Низький ризик, повністю оборотне, нуль впливу на роботу юзера (напр., фіксація події нижче порогу, додавання в watchlist) | Дія/спостереження + запис у журнал; власнику — лише в денному дайджесті |
| **L1 — auto + негайний сигнал** | D1, D3, D5, D7; D2/D4 — первинне стримування | Дія виконується одразу (ціна зволікання — атакуючий усередині), власник **у ту саму хвилину** отримує вердикт із кнопками відкату |
| **L2 — confirm ДО дії** | Freeze > 4 год, продовження freeze, freeze акаунта самого власника/адміна, вимкнення правила, яке власник раніше свідомо схвалив | Агент готує bundle + рекомендацію і **чекає** тап власника; без відповіді за 60 хв — ескалація повторним сигналом, дії немає |

Захист від «втоми від алертів»: один інцидент = один сигнал (агрегація повторів детектора по актору на 1 год), дайджест L0 — раз на день, пороги тюняться на онбордингу під реальний трафік клієнта (перші 7 днів пілота — режим observe: детектори рахують, дії — тільки L1-сигнали без виконання, калібрування порогів).

## 8. Безпека самого агента

Агент — найпривілейованіша сутність у тенанті клієнта, тому його компрометація не повинна означати компрометацію тенанта:

- **Окремий сервісний акаунт / Entra app** на клієнта, жодного перевикористання людських кредів; ключі — у секрет-менеджері (не у коді, не в репозиторії), ротація ≤ 90 днів.
- **Least privilege, роздільні ролі:** (а) Reader — тільки читання логів/метаданих; (б) Responder — вузький write: `suspend/unsuspend`, revoke tokens, зміна Drive permissions, disable mail rules. Два різні креденшали, Responder-кред активується тільки на час дії.
- **ЖОДНИХ delete-прав — принципово:** у Google — без `admin.directory.user.delete`, без Gmail delete scope (карантин = label/move, не `messages.delete`); у Microsoft — без `User.ReadWrite.All` у частині delete, без Mailbox delete. Навіть скомпрометований агент не може нічого знищити — максимум тимчасово заблокувати, і це відкочується.
- **Allowlist дій у коді:** ActionEngine має закритий перелік методів (§5); «виконати довільний API-виклик» інтерфейсу не існує.
- **Власний аудит:** кожна дія агента пишеться у той самий append-only журнал, що й інциденти; журнал агента доступний власнику клієнта повністю — клієнт бачить усе, що агент робив, включно з dry-run.
- **Dry-run за замовчуванням** у пілоті й на онбордингу кожного нового клієнта; бойовий режим — окремий прапор у конфігу, який вмикає власник.
- **Kill-switch:** власник однією дією (відкликати DWD-грант / disable Entra app) повністю відʼєднує агента; тенант при цьому лишається в стані «як було», незавершені freeze мають авто-розморозку за розкладом навіть без агента (де платформа дозволяє — через заплановану задачу на боці клієнта; чесне обмеження: у Google авто-unsuspend без зовнішнього тригера немає — тому freeze у пілоті ≤ 4 год і завжди з сигналом власнику).

## 9. Логування

- **Структуровані логи** (JSON, UTC, `incident_id` як correlation id крізь ingest → detector → action → notify).
- Три потоки: `ingest.log` (що прочитано з API, курсори/водяні знаки), `decisions.jsonl` (кожен Finding: спрацював/не спрацював поріг і чому — для тюнінгу й розбору false positive), `actions.jsonl` (кожна дія + rollback-статус).
- Ретеншн пілота: 90 днів локально; інцидентні bundle — безстроково (це докази клієнта).
- Жодних секретів, токенів і тіл листів у логах: тільки метадані й ID обʼєктів. Вміст — тільки в evidence bundle, і тільки для обʼєктів інциденту.

## 10. Пілот на власному Workspace (як розгортаємо на собі)

1. **Тиждень 0 (зараз):** прототип `watchdog.py` — детектори D1–D7 на синтетичних подіях, dry-run, evidence bundle з hash-chain, 3 симуляції (`impossible_travel`, `mass_download`, `public_link`). Демо, яке можна показати клієнту за 5 хвилин.
2. **Тиждень 1:** підключення **read-only** до власного Google Workspace (Reports/Drive/Gmail metadata), режим observe на живому трафіку, калібрування порогів, щоденний дайджест головному.
3. **Тиждень 2:** Responder-кред (вузький write), бойові оборотні дії на власному тенанті, тест відкату по кожній дії з §5 (контрольований інцидент на тестовому акаунті: публічний лінк + impossible travel із VPN).
4. **Критерій готовності до клієнтського пілота:** усі 7 детекторів спрацювали на контрольованих тестах, усі відкати пройшли, жодної дії без попереднього bundle, false positive ≤ погодженого порогу на живому тижні observe.

## 11. Roadmap пілот → продукт

| Етап | Зміст | Вихід |
|---|---|---|
| **P0 Прототип** (зараз) | Цей документ + `watchdog.py`, dry-run симуляції | Демо + evidence bundle |
| **P1 Свій тенант** | Read-only observe → оборотні дії на пілотний Workspace, M365-адаптер ingestion (read) | Калібровані пороги, звіт пілота |
| **P2 Клієнтський пілот** | 1 клієнт, 30 днів безкоштовно: observe 7 днів → active; онбординг-чекліст (аудит увімкнено? MFA? dormant-акаунти?) як безкоштовний «звіт про гігієну» — частина цінності навіть без інцидентів | Кейс + відгук + конверсія в підписку |
| **P3 Продукт v1** | Мультитенантність (окрема ізоляція кредів/даних на клієнта), панель власника (інциденти, відкати, дайджести), білінг підписки, алерт-канал у месенджер клієнта | Продаваний сервіс |
| **P4 Розширення** | Нові детектори за статистикою інцидентів (BEC-евристики, аномальний обсяг вихідної пошти), інтеграція техвідділу: виклик клієнта «щось не так» → технік бачить bundle й веде інцидент до кінця в одному вікні | Підвищення ціни/утримання |

**Поза roadmap свідомо:** EDR, антивірус, мережевий периметр, IR-послуги з виїздом — не наш продукт; партнерство/реферал, не розробка.
